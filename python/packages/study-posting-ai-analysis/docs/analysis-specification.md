# AI-Assisted Study Posting Authoring: Analysis Specification

**Status:** Specification of record for study-posting analysis policy,
classification, and interpretation.

If implementation and this document disagree, either the implementation is
incorrect or this specification must be amended in the same change.

Related documentation:

- [study-analysis flow](program-flow.md);
- [generic metric methodology](../../text-post-edit-metrics/docs/methodology.md);
- [generic metric verification](../../text-post-edit-metrics/docs/verification.md).

---

## 1. Purpose

This document defines the analysis used to evaluate the **AI-Assisted Study
Posting Authoring** feature, also referred to as AI-Assisted Study Posting
Creation.

The feature generates suggestions for fields in a study-posting form. Analysis
inputs capture:

1. suggestions generated by the AI;
2. suggestions or lookup values selected or applied by the user;
3. values ultimately saved by the user.

The analysis addresses related but distinct questions:

- How often did the AI provide a suggestion?
- How often was an offered suggestion selected?
- What happened to a selected suggestion before the posting was saved?
- How much technical text post-editing was required?
- Did conclusions remain similar under supporting text metrics?
- How closely did AI-assisted lookup selections match final saved sets?
- Was the suggested compensation Boolean retained?
- Which fields appear to receive the greatest proportional or absolute textual
  assistance?

The analysis estimates:

- suggestion offer coverage;
- suggestion selection;
- textual retention;
- technical post-editing burden;
- realized textual assistance;
- lookup-set retention;
- compensation-Boolean acceptance.

It does not directly measure:

- elapsed time;
- cognitive effort;
- observed keystrokes;
- semantic equivalence;
- user satisfaction;
- overall feature usefulness.

## 2. Inputs and library boundary

Each analysis call receives three objects.

| Input | Meaning |
|---|---|
| Suggested object | AI-generated text suggestions, lookup IDs, contact suggestions, compensation suggestions, and the suggested `offersCompensation` Boolean |
| Selected object | Suggestions or lookup IDs selected or applied by the user |
| Final object | Values ultimately saved in the study posting |

For text fields:

- the selected suggestion is treated as the initial text;
- the final saved value is treated as its represented edited form.

For the compensation Boolean:

- the suggested value represents the AI recommendation;
- the final value represents what the user ultimately saved.

### Upstream dataset selection and source mapping

A reporting source may select completed AI attempts upstream, for example:

```text
ATTEMPT_TYPE = 'AI'
ATTEMPT_RESULT = 'COMPLETE'
```

That filter is not required or enforced by either `study-posting-ai-analysis` or `study-posting-audit-report`. The reportingprogram determines row handling from the presence of its three analysis payloads:

- all three payloads present: analyze the row;
- all three payloads null: skip analysis while preserving the source record;
- partial payload presence: reject the inconsistent row.

The reporting program maps source columns to library inputs:

| Source column | Library input |
|---|---|
| `LLM_SUGGESTIONS` | Suggested object |
| `SELECTED_SUGGESTIONS` | Selected object |
| `FINAL_SUBMISSION` | Final object |

Upstream filtering, payload-state policy, and source mapping are not enforced by `study-posting-ai-analysis`.

The library performs no:

- database access;
- SQL execution;
- record eligibility filtering;
- CSV or filesystem I/O;
- DataFrame construction;
- logging;
- command-line processing;
- batch iteration;
- report publication.

A consuming program is responsible for:

- obtaining records;
- selecting eligible records;
- mapping source fields to the three inputs;
- assigning record identifiers;
- handling per-record failures;
- aggregating results;
- writing output.

## 4. Requiredness

Requiredness is enforced before normalized post-editing metrics are calculated.

| Field | Rule |
|---|---|
| `title` | Required |
| `purpose` | Required |
| `description` | Required |
| `about` | Optional |
| `contact.email` | Required |
| `contact.name` | Required |
| `contact.phone` | Optional |
| `contact.website` | Optional |
| Compensation text | Required exactly when final saved `offersCompensation` is `True` |
| `offersCompensation` | Must be saved as `True` or `False` |

A blank required field raises `ValueError`. It is not assigned a score of zero.

If a suggestion was selected for an optional field and the final value was
cleared, the outcome is `REMOVED`.

If no suggestion was selected for an optional blank field, the outcome is
`UNASSISTED`.

Normalized post-editing metrics are not calculated for a blank final value
because their final-length denominator would be zero.

## 5. Outcome vocabulary

### 5.1 Text outcomes

| Outcome | Meaning |
|---|---|
| `EXACT` | Selected and final Python strings are exactly equal |
| `COSMETIC_EQUIVALENT` | Strings differ but become equal under the study's cosmetic-equivalence transformation |
| `EDITED` | A suggestion was selected, the final value is nonblank, and substantive differences remain |
| `REMOVED` | A suggestion was selected for an optional field, then the final value was cleared |
| `UNASSISTED` | No AI-provided text suggestion was selected |

Text classification uses this order:

```text
blank → exact → cosmetic-equivalent → edited
```

The order is significant. Equal blank values on an optional selected field are
classified as `REMOVED`, not `EXACT`.

### 5.2 Lookup outcomes

| Outcome | Meaning |
|---|---|
| `EXACT` | Picked and final saved lookup sets are identical |
| `EDITED` | At least one AI-offered value was picked, but picked and saved sets differ |
| `UNASSISTED` | No AI-offered lookup value was picked |

## 6. Cosmetic-equivalence policy

Cosmetic equivalence is a study-product classification rule. It is separate from
generic metric preprocessing.

The transformation applies, in order:

1. Unicode compatibility decomposition using `NFKD`;
2. Unicode-aware case folding;
3. removal of combining marks, including decomposed diacritics;
4. replacement of punctuation and symbols with spaces;
5. whitespace collapsing and trimming.

Differences involving capitalization, punctuation, symbols, diacritics, or
repeated whitespace may therefore be classified as
`COSMETIC_EQUIVALENT`.

This transformation is used only for classification.

Cosmetically transformed text must never be passed to the technical text metrics
because doing so would hide actual textual changes. The original selected and
final strings are passed to `text_post_edit_metrics.analyze_post_edit()`.

### Policy-adjusted text score

| Outcome | Policy-adjusted score |
|---|---:|
| `EXACT` | `1.0` |
| `COSMETIC_EQUIVALENT` | `1.0` |
| `EDITED` | Bounded TER-derived score |
| `REMOVED` | `0.0` |
| `UNASSISTED` | `0.0` |

This is a product-policy score, not a standardized TER result.

## 7. Adopted text post-editing metrics

Technical text calculations are implemented by the sibling
[`text-post-edit-metrics`](../../text-post-edit-metrics/) package.

Canonical generic documentation:

- [methodology](../../text-post-edit-metrics/docs/methodology.md);
- [verification](../../text-post-edit-metrics/docs/verification.md).

`study-posting-ai-analysis` determines when a comparison applies and attaches
the returned `PostEditingResult` to the corresponding field analysis.

It does not implement:

- TER;
- character-level Levenshtein distance;
- weighted soft-word distance;
- generic metric normalization.

### 7.1 Study adoption profile

| Study choice | Adopted configuration |
|---|---|
| Comparison direction | Selected or applied suggestion → final saved text |
| Generic entry point | `text_post_edit_metrics.analyze_post_edit()` |
| Generic result | `PostEditingResult` |
| Primary measure | Bounded TER-derived effort saved |
| Primary raw diagnostic | `1 - TER`, retained even when negative |
| Supporting measures | Character and weighted soft-word effort saved |
| Absolute proxy | Estimated characters saved |
| Metric normalization | Unicode NFC |
| TER case behavior | Case-insensitive |
| Character case behavior | Case-sensitive |
| Soft-word case behavior | Case-sensitive |
| Soft-word tokenization | Whitespace-delimited |
| Empty suggestion | Valid |
| Blank final text | Not measurable; handled by study field policy |
| Metric package | `text-post-edit-metrics` 0.1.x |

### 7.2 Primary TER-derived measure

The study reports:

```text
ter_effort_saved_raw = 1 - ter_rate

ter_effort_saved =
    min(1, max(0, ter_effort_saved_raw))
```

TER uses final reference length as its denominator and may exceed `1`. The raw
score may therefore be negative.

`ter_effort_saved` is the primary bounded result for selected, nonblank text.

The raw value is retained because bounding all negative values to zero would hide
especially costly comparisons.

The study uses an **HTER-style interpretation** because selected or applied
model text is compared with the final saved form value.

This does not prove that:

- the final value was actually produced by editing the suggestion;
- editing activity was observed;
- the comparison reproduces a targeted human translation-annotation protocol.

### 7.3 Supporting measures

The study retains:

- character-level Levenshtein distance and effort-saved scores;
- weighted soft-word distance and effort-saved scores;
- estimated characters saved;
- suggestion and final character counts;
- suggestion and final whitespace-token counts.

Character and soft-word measures are supporting robustness measures. They do not
replace the primary TER-derived result.

Estimated characters saved is an absolute technical-editing proxy:

```text
max(0, final_character_count - character_edit_distance)
```

It is not:

- an observed count of avoided characters;
- an observed keystroke count;
- a direct measurement of time saved.

### 7.4 Interpretation

These measures quantify textual transformation.

They must not be interpreted as direct measures of:

- elapsed time;
- cognitive effort;
- observed keystrokes;
- semantic equivalence;
- user satisfaction;
- overall usefulness.

Complete formulas, preprocessing details, operation costs, result definitions,
and generic interpretation limits are maintained in the canonical
[`text-post-edit-metrics` methodology](../../text-post-edit-metrics/docs/methodology.md).

## 8. `PostEditingResult` in study analysis

`PostEditingResult` is defined by `text-post-edit-metrics`.

It contains generic metric values and text counts only. It does not contain:

- a study-posting field name;
- a record identifier;
- source information;
- selection state;
- product-policy classification.

Field identity remains in:

- the key of the `analyze_objects()` result dictionary;
- `TextFieldAnalysis.pick.kind` when a suggestion was selected;
- `field_name` in flattened output.

A `PostEditingResult` is attached only when:

1. a text suggestion was selected or applied;
2. the final saved value is nonblank.

It is `None` for `UNASSISTED` and `REMOVED`.

### 8.1 Result groups used by the study

| Group | Fields |
|---|---|
| TER | `ter_rate`, `ter_effort_saved_raw`, `ter_effort_saved` |
| Character | `character_edit_distance`, `character_effort_saved_raw`, `character_effort_saved` |
| Soft-word | `soft_word_edit_distance`, `soft_word_effort_saved_raw`, `soft_word_effort_saved` |
| Absolute proxy | `estimated_characters_saved` |
| Character counts | `suggestion_character_count`, `final_character_count` |
| Token counts | `suggestion_word_count`, `final_word_count` |

The canonical field reference is maintained in the
[`PostEditingResult` methodology section](../../text-post-edit-metrics/docs/methodology.md#9-posteditingresult).

### 8.2 Study-level questions

| Question | Study value |
|---|---|
| What is the conventional TER rate? | `ter_rate` |
| What is the primary bounded post-editing result? | `ter_effort_saved` |
| Did TER exceed final reference length? | `ter_effort_saved_raw` |
| Do conclusions hold at character level? | `character_effort_saved` |
| Do conclusions hold under fractional within-word substitutions? | `soft_word_effort_saved` |
| What is the absolute retained-character proxy? | `estimated_characters_saved` |
| What happened to the selected suggestion? | `TextFieldAnalysis.match` |
| What product-policy credit did the field receive? | `TextFieldAnalysis.policy_adjusted_effort_saved` |

## 9. Study and metric preprocessing boundaries

Generic metric preprocessing belongs to `text-post-edit-metrics`.

Under the adopted combined configuration:

- inputs are normalized with Unicode NFC;
- TER is case-insensitive;
- character distance is case-sensitive;
- soft-word distance is case-sensitive;
- soft-word tokenization uses whitespace;
- punctuation remains attached to tokens;
- hyphenated expressions remain one token;
- no stemming, lemmatization, or semantic normalization is performed.

The study cosmetic-equivalence transformation is separate. It uses:

- NFKD decomposition;
- case folding;
- combining-mark removal;
- punctuation-to-space replacement;
- whitespace collapsing.

Cosmetically transformed text is used only for classification.

The original selected and final strings are passed to `analyze_post_edit()`.
This preserves capitalization, punctuation, diacritic, and whitespace changes in
the underlying metrics.

## 10. Compensation analysis

Compensation contains two distinct components:

1. suggested and saved `offersCompensation` Boolean values;
2. optional categorized compensation text.

The final saved Boolean determines whether compensation text is required:

- saved `True` → text required;
- saved `False` → text optional.

Compensation-text categories:

- `genericCompensation`;
- `specificCompensation`.

At most one compensation-text suggestion may be selected across both categories.

### Boolean result fields

| Field | Meaning |
|---|---|
| `flag_suggested` | AI-recommended Boolean, if available |
| `flag_saved` | Final saved Boolean |
| `flag_accepted` | Whether saved matched suggested; `None` when not comparable |
| `flag_changed` | Whether saved differed from suggested; `None` when not comparable |
| `compensation_text_required` | Whether final saved Boolean requires text |

Examples:

| Scenario | Text outcome |
|---|---|
| AI suggested `False`; user saved `True` and wrote text independently | `UNASSISTED` |
| User selected text, saved `False`, and cleared text | `REMOVED` |

Boolean acceptance and compensation-text post-editing must be reported
separately.

## 11. Lookup analysis

Lookup fields contain integer ID sets rather than free text.

Booleans are rejected because Python treats `bool` as a subclass of `int`.

Every picked ID must have been offered.

For assisted outcomes:

```text
lookup_similarity =
    |picked ∩ saved| / |picked ∪ saved|
```

### Result sets

| Field | Meaning |
|---|---|
| `offered` | All IDs offered by the AI |
| `picked` | AI-offered IDs selected by the user |
| `saved` | Final IDs saved |
| `kept` | Picked IDs retained in saved |
| `dropped` | Picked IDs absent from saved |
| `added` | Saved IDs absent from picked |
| `saved_not_offered` | Saved IDs absent from every AI offer |

When no offered ID was picked:

- outcome = `UNASSISTED`;
- similarity = study-policy value `0.0`;
- no empty-set Jaccard calculation is performed.

Lookup similarity and text effort-saved scores measure different constructs and
must not be combined into one average.

## 12. Aggregate reporting vocabulary

The following statistics use different denominators and must be reported
separately.

| Statistic | Definition | Recommended label |
|---|---|---|
| Offer coverage | Text fields with at least one offer divided by all analyzed text fields | Suggestion offer coverage |
| Selection rate | Selected text fields divided by text fields with an offer | Suggestion selection rate |
| Realized utility among offers | Mean policy score among text fields with an offer | Realized suggestion utility |
| Utility among selected suggestions | Mean policy score among selected text fields | Selected-suggestion utility |
| TER score among measurable post-edits | Mean bounded TER-derived score among selected, nonblank suggestions | TER-derived post-editing score |
| Compensation Boolean acceptance | Saved Boolean matching suggested Boolean divided by comparable records | Compensation flag acceptance rate |
| Lookup similarity | Jaccard or policy-assigned similarity summarized by lookup field | Lookup similarity |

Every reported mean must identify its denominator or sample count.

Do not:

- label an all-text-fields average simply as “effort saved”;
- combine lookup similarity with text metrics;
- combine compensation-Boolean acceptance with compensation-text metrics.

Field-level summaries should accompany overall summaries because fields differ in
length and purpose.

## 13. Analysis flow

Within this library:

1. Optionally call `parse_analysis_inputs()` to decode the three JSON objects.
2. Call `analyze_objects()` to validate and dispatch configured fields.
3. Ordinary text routes to `analyze_text_field()`.
4. Contact routes to `analyze_contact()`.
5. Compensation routes to `analyze_compensation()`.
6. Lookup fields route to `analyze_lookup_values()`.
7. Selected, nonblank text passes to
   `text_post_edit_metrics.analyze_post_edit()`.
8. The returned `PostEditingResult` is attached to the field result.
9. Optionally call `flatten_analysis_results()` to produce one plain dictionary
   per field.

A consuming program is responsible for:

1. obtaining records;
2. selecting eligible records;
3. mapping source values to the three inputs;
4. deciding whether failed records stop or are skipped;
5. aggregating result types separately;
6. writing reports or output files.

### Validation performed by the library

The library verifies that:

- top-level fields are configured;
- text-suggestion containers contain strings;
- at most one ordinary text suggestion is selected;
- a selected text suggestion was offered;
- required text fields are nonblank;
- contact fields are recognized;
- compensation selection and Boolean rules hold;
- lookup IDs are integers and not Booleans;
- picked lookup IDs were offered.

Free text is excluded from flattened rows by default.

## 15. Interpretation limits

The metrics quantify textual transformation and estimate technical post-editing
burden.

They do not directly measure:

- cognitive effort;
- reading or deliberation time;
- elapsed task time;
- observed keystrokes;
- cursor movement;
- block selection;
- copy, paste, or undo operations;
- whether a suggestion changed the user's ideas;
- whether the final text was actually produced by editing the suggestion;
- semantic equivalence;
- user satisfaction;
- perceived helpfulness.

A small textual change may follow substantial deliberation. Conversely, a large
textual replacement may be easy despite a large edit distance.

Claims about time, cognition, or overall utility require external validation,
such as:

- task-completion time;
- editing-event logs;
- observed keystrokes;
- user ratings;
- qualitative feedback;
- comparison with a no-suggestion condition.

This analysis supports claims about:

- textual retention;
- post-editing burden;
- suggestion uptake;
- realized textual assistance.

## Appendix A. Methodological summary

> Selected AI text was compared directionally with final saved text under a
> post-editing interpretation. The primary measure was bounded TER-derived
> effort saved, with the unbounded raw value retained for diagnostics.
>
> Supporting measures included character-level Levenshtein effort saved, a
> custom weighted soft-word effort-saved score, and estimated characters saved.
>
> Metric inputs used Unicode NFC. TER was case-insensitive; character and
> soft-word measures were case-sensitive. Soft-word tokenization used whitespace
> boundaries, with no stemming, lemmatization, or semantic normalization.
>
> These measures quantify textual transformation. They should not be interpreted
> as direct measurements of elapsed time, cognitive effort, observed keystrokes,
> semantic equivalence, or user satisfaction.
