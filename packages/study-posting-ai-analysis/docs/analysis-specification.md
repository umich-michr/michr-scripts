# AI-Assisted Study Posting Authoring: Analysis Specification

**Status:** specification of record. If the implementation and this document
disagree, this document governs — or it must be amended in the same change.

See [`program-flow.md`](program-flow.md) for control-flow and architecture
diagrams.

---

## 1. Purpose

This document defines the analysis used to evaluate the **AI-Assisted Study
Posting Authoring** feature, also referred to as AI-Assisted Study Posting
Creation.

The feature generates suggestions for fields in a study posting form. Audit
records capture:

1. the suggestions generated by the AI;
2. which suggestions, if any, were selected or applied;
3. the final values saved by the user.

The analysis uses these records to answer related but distinct questions:

- How often did the AI provide a suggestion?
- How often was an offered suggestion selected?
- How much of a selected text suggestion survived into the final posting?
- How much textual post-editing was required?
- Did the result remain favorable under alternative text-editing measures?
- How closely did AI-assisted lookup selections match the final saved sets?
- Was the AI-suggested compensation radio-button value retained?
- Which form fields appear to receive the greatest proportional and absolute
  benefit?

The analysis estimates **realized textual assistance** and **technical
post-editing effort**. It does not directly measure cognitive effort, elapsed
time, observed keystrokes, or user satisfaction.

---

## 2. Audit-record inputs

Each analyzed posting has three input objects.

| Input | Description |
|---|---|
| Suggested object | All AI-generated suggestions: text suggestions, lookup IDs, contact suggestions, compensation suggestions, and the suggested `offersCompensation` Boolean. |
| Selected object | Suggestions or lookup values selected or applied in the user interface. |
| Final object | Values ultimately saved in the study posting. |

For text fields, the selected suggestion is the starting text and the final saved
value is treated as its human-edited result.

For the compensation radio button, the suggested Boolean may be propagated
automatically into the interface. The final saved Boolean represents the value
retained or changed by the user.

### Upstream dataset inclusion rule

The study's planned audit-reporting program includes rows where
`ATTEMPT_TYPE = 'AI'` and `ATTEMPT_RESULT = 'COMPLETE'`. It maps the
`LLM_SUGGESTIONS`, `SELECTED_SUGGESTIONS`, and `FINAL_SUBMISSION` columns to the
three objects accepted by this library.

This eligibility rule and database-column mapping are **not enforced by
`study-posting-ai-analysis`**. The library performs no database access and has
no knowledge of an audit-table schema. A consuming program is responsible for
selecting records and supplying the three inputs.

## 3. Fields covered by the analysis

### Text fields

`title`, `purpose`, `description`, `about`, compensation text,
`contact.email`, `contact.name`, `contact.phone`, `contact.website`

### Lookup fields

`department`, `locations`, `topics`

### Compensation Boolean

`offersCompensation`

The Boolean is incorporated into the compensation analysis rather than reported

## 4. Field-requiredness rules

Requiredness is enforced **before** normalized post-editing metrics are
calculated.

| Field | Rule |
|---|---|
| `title` | Required |
| `purpose` | Required |
| `description` | Required |
| `about` | Optional |
| `contact.email` | Required |
| `contact.name` | Required |
| `contact.phone` | Optional |
| `contact.website` | Optional |
| Compensation text | Required when the final saved `offersCompensation` is `True`; optional when `False` |
| `offersCompensation` | Must be saved as `True` or `False` |

A blank required field is rejected as invalid. It is an error, not a metric of
zero.

If a suggestion was selected for an optional field and the final value was
cleared, the outcome is `REMOVED`. Normalized post-editing metrics are not
calculated, because the final-length denominator would be zero.

If no suggestion was selected for an optional blank field, the outcome is
`UNASSISTED`.

## 5. Outcome vocabulary

### Text outcomes

| Outcome | Meaning |
|---|---|
| `EXACT` | The selected suggestion and final saved Python strings are exactly equal. |
| `COSMETIC_EQUIVALENT` | The strings differ but become equal after the cosmetic-equivalence transformation. |
| `EDITED` | A suggestion was selected or applied, the final value is nonblank, and substantive textual differences remain. |
| `REMOVED` | A suggestion was selected for an optional field, but the final saved value is blank. |
| `UNASSISTED` | No AI-provided text suggestion was selected. The final value may have been written independently, or may be blank when the field is optional. |

### Lookup outcomes

| Outcome | Meaning |
|---|---|
| `EXACT` | The picked and final saved lookup sets are identical. |
| `EDITED` | At least one AI-offered value was picked, but the picked and final sets differ. |
| `UNASSISTED` | No AI-offered lookup value was picked. |

## 6. Cosmetic-equivalence classification

Cosmetic equivalence is a **product-level classification rule**. It is
deliberately separate from the preprocessing used by the edit metrics.

The transformation performs, in order:

1. Unicode compatibility decomposition using `NFKD`;
2. Unicode-aware case folding;
3. removal of combining marks, including decomposed diacritics;
4. replacement of punctuation and symbols with spaces;
5. whitespace collapsing and trimming.

Differences involving capitalization, punctuation, diacritics, or repeated
whitespace may therefore be classified as `COSMETIC_EQUIVALENT`.

This broad transformation is used **only** for classification. It must never be
used to calculate TER, character-level Levenshtein distance, or weighted
soft-word distance; doing so would hide actual textual edits.

### Policy-adjusted score

| Outcome | Policy-adjusted score |
|---|---|
| `EXACT` | `1` |
| `COSMETIC_EQUIVALENT` | `1` |
| `EDITED` | the bounded TER-derived score |
| `REMOVED` | `0` |
| `UNASSISTED` | `0` |

The policy-adjusted score is stored separately from the underlying TER-derived
result.

## 7. Text post-editing metrics

The calculations in this section are implemented by the reusable
`michr-text-post-editing` package. `study-posting-ai-analysis` determines when a
text comparison applies and stores the returned `PostEditingResult` on the
corresponding field analysis; it does not implement these algorithms itself.

The formulas remain part of this study specification because they define the
meaning of the study's reported text metrics.

### 7.1 Primary metric: TER-derived effort saved

Translation Edit Rate (TER) evaluates the word-level editing required to
transform a system output into a reference text. TER considers word insertion,
word deletion, word substitution, and movement of a contiguous word sequence
(a shift). TER is normalized by the length of the final reference.

In this analysis:

- system output = the selected or applied LLM suggestion;
- human-edited reference = the final saved form text.

This is described as an **HTER-style** application because an applied model
output is compared with its final human-edited result. It is not presented as an
exact replication of the targeted human translation-annotation protocol.

**Formulas**

```
TER                  = TER edit cost / final reference length
ter_effort_saved_raw = 1 - TER
ter_effort_saved     = min(1, max(0, ter_effort_saved_raw))
```

**Interpretation**

| Value | Interpretation |
|---|---|
| `ter_rate = 0` | No TER edits were required. |
| `ter_rate = 0.25` | TER edit cost equaled roughly one quarter of the final reference length. |
| `ter_rate = 1` | TER edit cost equaled the final reference length. |
| `ter_rate > 1` | TER edit cost exceeded the final reference length. |
| `ter_effort_saved = 1` | No TER edits were required. |
| `ter_effort_saved` near `1` | Relatively little post-editing was required. |
| `ter_effort_saved = 0` | TER reached or exceeded the final-length baseline. |
| `ter_effort_saved_raw < 0` | TER exceeded the final-length baseline. |

`ter_effort_saved` is the **primary bounded result** for reporting selected,
nonblank text suggestions.

`ter_effort_saved_raw` is retained because clamping negative values to zero
would otherwise remove information about particularly costly suggestions.

The effort-saved transformation is a directional technical-editing proxy. It must
not be interpreted as the literal percentage of time, thought, or keystrokes
saved.

**Software configuration**

TER is calculated with SacreBLEU 2.6.x using:

```
normalized     = False
no_punct       = False
asian_support  = False
case_sensitive = False
```

TER is therefore **case-insensitive** under this configuration.

### 7.2 Character-level technical-editing measure

Character-level Levenshtein distance calculates the minimum number of
single-character insertions, deletions, and substitutions required to transform
the suggestion into the final text.

```
character_effort_saved_raw = 1 - character_distance / final_character_count
character_effort_saved     = min(1, max(0, character_effort_saved_raw))
```

**Interpretation**

- A distance of `0` means the NFC-normalized strings are identical.
- A higher distance means more character-level modification.
- A bounded score of `1` means no character edits were required.
- A score near `0` indicates the distance approached or exceeded the final
  character count.

This is a character-level **technical-editing proxy**, not an observed keystroke
count. Actual editing can involve block selection, copy and paste, cursor
movement, and undo operations.

The character-level calculation **preserves case and punctuation**.

### 7.3 Weighted soft-word robustness measure

A custom weighted word-level edit distance.

At the word level:

- insertion cost = `1`;
- deletion cost = `1`;
- substitution cost = the **normalized** character-level Levenshtein distance
  between the two words.

Character-similar substitutions therefore receive fractional costs. A change such
as `analyze` to `analyzed` generally costs less than replacing `analyze` with an
orthographically unrelated word.

The algorithm calculates the minimum-cost sequence of insertions, deletions, and
substitutions using a weighted Wagner–Fischer dynamic-programming recurrence.

```
soft_word_effort_saved_raw = 1 - soft_word_distance / final_word_count
soft_word_effort_saved     = min(1, max(0, soft_word_effort_saved_raw))
```

**Interpretation**

The soft-word result is a **supporting robustness measure**. It tests whether
conclusions remain similar when small within-word changes receive partial credit
rather than being charged as complete word substitutions. It must not replace the
primary TER-derived result unless separately validated for that purpose.

Unlike TER, the soft-word implementation does **not** include phrase-shift
operations.

### 7.4 Estimated characters saved

```
estimated_characters_saved = max(0, final_character_count - character_distance)
```

This is numerically equivalent to multiplying the bounded character effort-saved
score by the final character count.

It helps distinguish proportional from absolute assistance. A long description
can have a lower proportional score than a short title while still representing
more retained text overall.

This field is **not** a literal measurement of characters the user avoided typing,
nor an observed keystroke count.

### 7.5 Bounded reporting score

For every raw effort-saved score:

```
bounded = min(1, max(0, raw))
```

Both the raw and bounded values are always stored. The raw value is never
discarded.

## 8. `PostEditingResult` field guide

`PostEditingResult` is defined by the reusable `michr-text-post-editing`
package. It contains only technical text-comparison results and does not contain
a study-posting field name.

Field identity is maintained by the surrounding `analyze_objects()` result
dictionary and, for selected suggestions, by `TextFieldAnalysis.pick.kind`.
This avoids duplicating form-specific context inside a reusable metric result.

Produced when a text suggestion was selected or otherwise applied **and** the
final saved text is nonblank. It is **not** produced for `UNASSISTED` or
`REMOVED` outcomes.

| Field | Definition | Recommended use |
|---|---|---|
| `ter_rate` | TER edit cost ÷ final reference length. Range starts at `0`; may exceed `1`. | Conventional edit-rate result. Lower is better. |
| `ter_effort_saved_raw` | `1 - ter_rate`. May be negative. | Directional diagnostic. Identifies cases where TER exceeded the final-length baseline. |
| `ter_effort_saved` | `ter_effort_saved_raw` bounded to `[0, 1]`. | **Primary bounded reporting value.** Higher is better. |
| `character_edit_distance` | Minimum character insertions, deletions, and substitutions. | Secondary character-level measure. Lower is better. Not an observed keystroke count. |
| `character_effort_saved_raw` | `1 - character_edit_distance / final_character_count`. May be negative. | Character-level directional robustness measure. |
| `character_effort_saved` | Bounded to `[0, 1]`. | Bounded character-level robustness result. |
| `soft_word_edit_distance` | Weighted word-level distance: insertion and deletion cost `1`; substitution costs the normalized character distance. | Supporting robustness measure. Lower is better. Custom robustness measure, not standardized TER. |
| `soft_word_effort_saved_raw` | `1 - soft_word_edit_distance / final_word_count`. May be negative. | Diagnostic soft-word result before clamping. |
| `soft_word_effort_saved` | Bounded to `[0, 1]`. | Bounded soft-word robustness result. |
| `estimated_characters_saved` | `max(0, final_character_count - character_edit_distance)`. | Absolute technical-editing proxy for comparing assistance across differently sized fields. |
| `suggestion_character_count` | Python characters in the NFC-normalized suggestion, including punctuation and whitespace. | Descriptive context; possible statistical control variable. Not a byte count. |
| `final_character_count` | Python characters in the NFC-normalized final text. | Character-score denominator and basis for the absolute proxy. Uses the actual length, not the field limit. |
| `suggestion_word_count` | Whitespace-delimited suggestion tokens. | Descriptive suggestion-length measure. Punctuation stays attached; hyphenated forms remain one token. |
| `final_word_count` | Whitespace-delimited final-text tokens. | Soft-word denominator. Must **not** be used to reconstruct TER, because SacreBLEU applies its own processing. |

### Which field answers which question?

| Question | Field |
|---|---|
| What is the conventional edit rate? | `ter_rate` |
| What is the primary bounded post-editing result? | `ter_effort_saved` |
| Did TER exceed the final-length baseline? | `ter_effort_saved_raw` |
| Do conclusions hold at the character level? | `character_effort_saved` |
| Do conclusions hold when within-word edits receive partial credit? | `soft_word_effort_saved` |
| Which fields received the greatest absolute textual benefit? | `estimated_characters_saved`, interpreted cautiously |
| Could text length explain differences between fields? | The four count fields |
| Was the outcome exact, cosmetic, edited, removed, or unassisted? | `TextFieldAnalysis.match` |
| Should a cosmetic-equivalent result receive full product credit? | `TextFieldAnalysis.policy_adjusted_effort_saved` |

### Example interpretation

Given `ter_rate = 0.20`, `ter_effort_saved = 0.80`,
`character_effort_saved = 0.90`, `soft_word_effort_saved = 0.86`,
`estimated_characters_saved = 180`:

> The TER edit cost was equivalent to 20% of the final reference length,
> producing a bounded TER-derived effort-saved score of 0.80. Character and
> soft-word robustness scores were also high, indicating the conclusion was not
> unique to the TER formulation. The character-level calculation yielded an
> absolute technical-editing proxy of 180 characters.

It would **not** be appropriate to conclude:

> The user saved exactly 80% of their time or avoided exactly 180 keystrokes.

## 9. Text preprocessing

All metric inputs are normalized using Unicode Normalization Form **NFC**.

Under this configuration:

- TER is case-insensitive;
- character-level calculations preserve case;
- soft-word calculations preserve case;
- soft-word tokenization uses whitespace boundaries;
- punctuation remains attached to adjacent soft-word tokens;
- hyphenated expressions remain single tokens;
- repeated whitespace does not change tokenization;
- no stemming is performed;
- no lemmatization is performed;
- no embedding, thesaurus, ontology, or semantic normalization is used.

Consequently, semantically similar but orthographically different expressions can
receive substantial substitution costs. For example, `physician` and `doctor` have
similar meanings but are treated as substantially different strings.

## 10. Compensation analysis

Two distinct components:

1. the AI-suggested `offersCompensation` Boolean;
2. an optional AI-generated compensation text suggestion.

The **final saved** Boolean determines whether compensation text is required:

- saved `True`: compensation text is required;
- saved `False`: compensation text may be blank.

| Field | Meaning |
|---|---|
| `flag_suggested` | AI-recommended value, or `None` if no recommendation was available. |
| `flag_saved` | Final Boolean saved by the user. |
| `flag_accepted` | Whether the final value matched the recommendation. `None` when no comparison is possible. |
| `flag_changed` | Whether the final value differed from the recommendation. `None` when no comparison is possible. |
| `compensation_text_required` | `True` exactly when `flag_saved` is `True`. |

Two cases worth noting:

- If the AI suggested `False`, the user changed the value to `True`, and wrote
  compensation text without selecting a suggestion, the text outcome is
  `UNASSISTED`.
- If compensation text was selected but later cleared after the Boolean was
  changed to `False`, the text outcome is `REMOVED`.

At most one compensation text suggestion may be selected across both categories
(`genericCompensation`, `specificCompensation`).

Boolean acceptance must be analyzed **separately** from compensation-text
post-editing scores.

## 11. Lookup analysis

Lookup fields contain sets of integer IDs rather than free text. Booleans are
rejected explicitly, because `bool` subclasses `int` in Python. Picked IDs must
have been among the offered IDs.

For assisted outcomes, similarity is Jaccard similarity:

```
lookup_similarity = size(picked ∩ saved) / size(picked ∪ saved)
```

| Value | Meaning |
|---|---|
| `1.0` | Picked and saved sets are identical. |
| `0.0` | The sets share no values. |
| Between `0` and `1` | Partial overlap. |

Also reported:

| Field | Meaning |
|---|---|
| `offered` | All IDs offered by the AI. |
| `picked` | AI-offered IDs selected by the user. |
| `saved` | Final IDs saved by the user. |
| `kept` | Picked IDs retained in the saved set. |
| `dropped` | Picked IDs absent from the saved set. |
| `added` | Saved IDs that were not among the picked values. |
| `saved_not_offered` | Saved IDs absent from all AI offers. |

When no AI-offered value was picked, the outcome is `UNASSISTED` and similarity is
assigned `0.0` as a **realized-assistance policy value**, not calculated from an
empty-set Jaccard formula, which would be undefined.

Lookup similarity is reported separately from text effort-saved scores. The two
must never be combined into a single average, because they measure different
constructs.

## 12. Aggregate reporting vocabulary

These statistics have different denominators and answer different questions. They
must be reported separately.

| Statistic | Definition | Label |
|---|---|---|
| Offer coverage | Text fields with at least one suggestion ÷ all analyzed text fields. | Suggestion offer coverage |
| Selection rate | Text fields with a selected suggestion ÷ text fields with at least one offer. | Suggestion selection rate |
| Realized utility among offers | Mean policy-adjusted score among text fields where at least one suggestion was offered. Offered-but-unselected and removed suggestions receive zero. | Realized suggestion utility |
| Utility among selected suggestions | Mean policy-adjusted score among selected suggestions. Removed suggestions receive zero. | Selected-suggestion utility |
| TER score among measurable post-edits | Mean bounded TER-derived score among selected suggestions with nonblank final text. | TER-derived post-editing score |
| Compensation Boolean acceptance | Saved Boolean matching the AI recommendation ÷ records with an AI recommendation. | Compensation flag acceptance rate |
| Lookup similarity | Jaccard or policy-assigned similarity, summarized separately by lookup field. | Lookup similarity |

**Every reported mean must identify its denominator or sample count.**

Do not report an all-text-fields average simply as "effort saved" without
explaining its denominator.

Field-level summaries should generally accompany overall summaries, because title,
description, purpose, contact, and compensation fields differ substantially in
length and function.

## 13. How the analysis is run

## 13. How the analysis is run

Within this library:

1. Optionally call `parse_analysis_inputs()` to decode the suggested, selected,
   and final JSON objects.
2. Call `analyze_objects()` to validate and analyze every configured field.
3. Text fields route to `analyze_text_field()`.
4. Contact subfields route to `analyze_contact()`.
5. Compensation routes to `analyze_compensation()`.
6. Lookup fields route to `analyze_lookup_values()`.
7. Selected nonblank text suggestions pass to
   `michr_text_post_editing.analyze_post_edit()`, which returns a
   `PostEditingResult`.
8. Optionally call `flatten_analysis_results()` to produce one plain dictionary
   per analyzed field.

Outside this library, a consuming program is responsible for:

1. obtaining records from a database, CSV file, HTTP request, or another source;
2. selecting eligible records;
3. mapping source fields to the three analysis inputs;
4. deciding whether a malformed record stops or is skipped by the run;
5. aggregating text, compensation, and lookup results separately; and
6. writing CSV files, DataFrames, database tables, or publication reports.

`study-posting-ai-analysis` performs no database, filesystem, DataFrame,
reporting, or logging I/O.

The study package does not implement TER, character distance, or weighted
soft-word distance. Those calculations and their low-level tests belong to
`michr-text-post-editing`. The study package determines when the calculation is
applicable and attaches the returned result to the appropriate field analysis.

The implementation validates that:

- top-level fields are recognized;
- text-suggestion containers contain strings;
- lookup IDs are integers and not Booleans;
- selected lookup IDs were offered;
- required text fields are nonblank;
- selected text suggestions occur among the AI suggestions;
- at most one text suggestion is selected per ordinary text field;
- at most one compensation text suggestion is selected;
- the required compensation Boolean is present.

Free text is excluded from exported rows by default, to reduce accidental
disclosure of potentially sensitive content.

## 14. Software verification

Verification is divided by package:

- `michr-text-post-editing` tests TER, character-level Levenshtein,
  weighted soft-word distance, normalization, raw and bounded formulas, and
  randomized differential agreement with a full-matrix implementation.
- `study-posting-ai-analysis` tests form requiredness, selection validity,
  outcome classification, compensation behavior, contact behavior, lookup
  analysis, JSON parsing, flattening, and integration with
  `PostEditingResult`.

### Scope

The automated tests provide evidence that the software correctly implements:

TER-derived metrics; character-level Levenshtein metrics; weighted soft-word
metrics; Unicode and case preprocessing; cosmetic-equivalence classification;
exact, edited, removed, and unassisted outcomes; required and optional field
rules; compensation behavior; contact-field processing; lookup analysis; CSV
flattening; and end-to-end object orchestration.

Passing tests demonstrate conformity between the software and the specified
calculations. They do **not** prove that the metrics measure human cognitive
effort, time saved, or overall usefulness.

### Identity and boundary conditions

Tests verify that:

- identical texts have distance `0` and bounded score `1`;
- an empty suggestion requires insertion of every final word or character;
- an empty final text requires deletion of every suggested word at the low-level
  distance layer;
- normalized metrics reject a zero-length final denominator;
- blank required fields are rejected;
- optional selected-to-blank outcomes are classified as `REMOVED`.

### Directional insertion and deletion costs

Tests assign unequal operation costs — insertion `2`, deletion `3` — and verify:

- `""` to `"word"` costs `2`;
- `"word"` to `""` costs `3`;
- insertion into a nonempty sequence uses the insertion cost;
- deletion from a nonempty sequence uses the deletion cost.

Unequal test costs detect a reversal that would remain hidden if both costs were
`1`.

### Unequal-length alignments

Tests include `very quickly` → `fast` and `fast` → `very quickly`, confirming that
every source and target word contributes to the distance and that no item is
silently omitted when sequence lengths differ.

### Fractional substitutions

Tests verify that character-similar word changes receive fractional costs; that
orthographically unrelated replacements cost more than small spelling or suffix
changes; that the exact RapidFuzz normalized character distance is used; and that
final word count is the soft-word denominator.

### Raw and bounded scores

Tests verify that raw effort-saved scores may be negative, that bounded scores
remain within `[0, 1]`, and that negative raw values are retained before
clamping.

### Preprocessing and validation

Tests cover Unicode NFC normalization; case-sensitive and case-insensitive
low-level calculations; case-sensitive study-level character and soft-word
calculations; case-insensitive TER; whitespace tokenization; cosmetic-equivalence
normalization; invalid operation costs; invalid text containers; invalid lookup
IDs; multiple compensation selections; compensation Boolean behavior; required and
optional fields; contact subfields; CSV flattening; and complete record
orchestration.

## 15. Randomized differential testing

Randomized differential testing belongs to `michr-text-post-editing`, which
owns the weighted soft-word algorithm.

Its production implementation retains only two rows of the dynamic-programming
matrix to reduce memory use. A separate full-matrix implementation is retained
in that package's test suite for verification.

The verification procedure:

1. Generate a suggestion/final pair.
2. Calculate weighted soft-word distance with the two-row implementation.
3. Calculate the same distance with the full-matrix implementation.
4. Compare the values to 12 decimal places.

The tests include:

- 1,000 pseudorandom pairs with insertion and deletion costs equal to `1`;
- 500 pseudorandom pairs with unequal insertion and deletion costs;
- empty and nonempty sequences;
- differing sequence lengths;
- repeated words;
- insertions, deletions, and substitutions.

Fixed random seeds are used for reproducibility. Across all 1,500 generated cases,
the optimized and full-matrix implementations agreed to 12 decimal places.

Because both implementations use the same recurrence and the same RapidFuzz
substitution-cost function, this verifies **implementation consistency** rather
than independently proving that the metric measures human effort.

## 16. Interpretation limits

The metrics quantify textual transformation and serve as proxies for **technical
post-editing effort**.

They do not directly measure:

- cognitive effort;
- reading or deliberation time;
- elapsed task time;
- observed keystrokes;
- cursor movement;
- block selection;
- copy, paste, or undo operations;
- whether the suggestion changed the user's ideas;
- semantic equivalence;
- user satisfaction;
- perceived helpfulness.

A user can make a small textual change after substantial deliberation, producing a
small edit distance despite high cognitive effort. Conversely, a large block can
be replaced easily in a graphical editor despite a large edit-distance cost.

Stronger claims about time saved, cognitive effort, or overall feature utility
require external validation, such as task-completion time, editing-event logs,
observed keystrokes, user helpfulness ratings, qualitative feedback, or comparison
with a no-suggestion control condition.

This analysis supports claims about **textual retention, post-editing burden,
suggestion uptake, and realized textual assistance**.

## Appendix A. Methodological summary

Suitable for a methods section.

> Editing effort was measured with a weighted dynamic-programming recurrence: the
> minimum-cost sequence of word insertions, deletions, and substitutions was
> calculated using a dynamic-programming edit-distance algorithm, with word
> substitutions receiving fractional costs based on character-level similarity.
>
> Words were identified using whitespace tokenization. No stemming or
> lemmatization was applied, and substitutions were evaluated from character
> overlap rather than semantic similarity. Consequently, semantically related but
> orthographically dissimilar words were treated as substantive substitutions.
>
> The primary measure was TER-derived effort saved, `1 − TER`, where TER
> calculates word-level insertion, deletion, substitution, and block-shift costs
> normalized by the length of the final reference text (Snover et al., 2006). For
> suggestions applied to an editable field, this was interpreted as an HTER-style
> technical post-editing setup.
>
> Two supporting measures were reported: character-level Levenshtein distance
> normalized by final text length (Levenshtein, 1966; Wagner & Fischer, 1974), and
> a weighted word-level distance in which insertions and deletions cost 1 and a
> substitution cost the normalized character-level distance between the two
> words.
>
> An absolute proxy, estimated characters saved, was calculated as the final
> character count minus the character-level edit distance, bounded below at zero.
> This is not a count of observed keystrokes or literal characters the user
> avoided typing.
